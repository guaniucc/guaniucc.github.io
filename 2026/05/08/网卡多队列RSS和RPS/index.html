为解决的问题

当数据包量过大时，网卡流量上不去，表现是连接会“断联”，但是从监控上看没有出现丢包情况（云数据库，DGW，云redis，容器node节点、vpn网关机等）

cpu软中断集中在cpu0 上，没有分流到其他cpu

一、设置RSS（硬件）

比如服务器的核数是8核（8颗cpu），则设置队列为8

二、设置RPS/RFS（软件）

/sys/class/net/eth0/queues/rx-0/rps_cpus 和 /sys/class/net/eth0/queues/rx-0/rps_flow_cnt 是 Linux 内核中用于 RPS (Receive Packet Steering) 的配置参数，主要用于在多核系统中优化网络数据包接收性能。

1. rps_cpus - CPU 亲和性位图

  • 作用: 指定哪些 CPU 核心可以处理来自该 RX 队列的网络数据包

  • 格式: 十六进制位图，每个位对应一个 CPU 核心

  • 示例:

    • 0f (二进制 1111) = CPU 0-3 可以处理
    • 01 (二进制 0001) = 仅 CPU 0 可以处理
    • ffff = CPU 0-15 都可以处理

tips：这里cpu0 就是 0001 ，cpu1就是0010 ， cpu2就是0100 以此类推，当需要设置全部8颗cpu时，就是将8个二进制数加起来，既11111111，对应ff。

2. rps_flow_cnt - 流表条目数

  • 作用: 定义用于流量分类的哈希表大小（影响流的识别和分发）
  • 单位: 条目数量
  • 影响: 值越大，不同网络流被区分得更细，减少哈希冲突

3. 使用场景

场景1：单队列网卡 + 多核CPU
  • 问题: 传统单队列网卡所有流量都由单个CPU处理（通常是CPU0）
  • 解决: 启用RPS将流量分摊到多个CPU
  • 配置示例:
场景2：CPU负载不均衡
  • 现象: 网络处理集中在少数几个CPU，其他CPU空闲
  • 解决: 调整rps_cpus让空闲CPU参与网络处理
场景3：高并发网络服务
  • 服务类型: Web服务器、代理服务器、数据库等
  • 需求: 需要充分利用多核处理网络请求
  • 优化: 配合RFS (Receive Flow Steering) 使用
场景4：虚拟机或容器环境
  • 场景: 虚拟化环境中网卡可能不支持多队列
  • 解决: 在宿主机或客户机中启用RPS

三、核心关系对比

特性 ethtool -L combined (RSS) RPS (Receive Packet Steering)
实现层级 硬件层面（网卡芯片） 软件层面（内核驱动）
硬件要求 需要网卡支持多队列 任何网卡都支持
性能 更高（硬件加速） 较低（软件处理）
CPU开销 低（硬件分流） 较高（软件分流）
配置位置 网卡驱动/固件 Linux内核参数

五、结论

核心关系：

  1. RSS (**ethtool -L combined**) 是首选方案，硬件加速，性能最好
  2. RPS 是补充方案，当硬件不支持或队列不足时使用
  3. 两者可以同时使用，形成两级分发（硬件+软件）
  4. 配置原则：尽可能用RSS，必要时用RPS补充
